- Assumption: quarters mean four traditional subdivisions of each Juz (120 quarter starts overall), not the 240 individual rub al-hizb marks. Handle boundaries inside pages, ayahs spanning pages and existing legacy Juz starts; verify against the printed markers rather than silently changing valid Juz destinations. - Use the existing onJumpToPage / onJumpToSurah and _jumpToReadingPage flow in lib/main.dart, preserving RTL spread alignment, focus, bookmarks, recent history and audio-follow behaviour. Use the actual boundary surah if needed to avoid stale current-surah context. Do not unexpectedly start audio, move within a page, or change reader zoom.
- Preserve independent tab scroll positions. Adapt NavigationListView item extents / initial offsets to expandable rows; prevent stale scroll extent and clipping after expansion. Keep current Juz highlighting and scroll-to-current on open, including cover pages and shared boundary pages. Avoid adding search fields, a third tab or unrelated UI.

## 2. Diagnose and improve audible ayah joins (all 22 reciters)

### Evidence from the repository

- ContinuousPcmBackend is the default iOS/Android backend; QuranAudioController selects it without a reciter-specific exception. PCM chunks are scheduled on one output rather than restarting playback for each MP3. Original quiet audio is preserved, and only known encoder metadata is used for trimming where supported.
- The all-22-reciter test (test/continuous_pcm_backend_test.dart, around lines 228–247) uses NativeClock and simulated one-second recordings. It demonstrates backend selection and queue logic, NOT native decoding or audible gaplessness.
- docs/audio-gap-analysis.json and docs/v5-gapless-validation.md did not include Abdullah Al-Juhany; existing Yasser proof is not evidence for him. docs/continuous-everyayah-engine.md explicitly leaves physical output acceptance pending.
- Al-Juhany's actual configured EveryAyah folder is Abdullaah_3awwaad_Al-Juhaynee_128kbps (lib/models/quran_audio.dart). User hears an audible cut when he connects adjacent ayahs. The source of this cut is not yet established; do not assume it is inherent to EveryAyah or already the best possible.

### Investigate before changing audio processing

1. Download byte-identical original recordings from EveryAyah for Al-Juhany first: several consecutive ayahs from Al-Ikhlas/Al-Falaq, Al-Rahman, and a passage with joined recitation; use the user's exact reported verse pair if available. Include Al-Baqarah 2:255 and 2:282 for long recordings. If direct retrieval fails, use the existing documented verified maqra mirror (abdullah-awad-al-juhani-128kbps), verify hashes against the provider where possible, and report verification limits. Keep originals unmodified.
2. Extend the existing FFmpeg/PCM audit and transition-probe tooling under tool/. Check source codec/sample rate/channels, decoded frame counts, encoder delay/padding, malformed/truncated frames and waveform edges. Compare metadata-aware reference concatenation with native decoded frame boundaries and captured playback output. Inspect audible joins for silence, clicks/discontinuities, missing or duplicated pronunciation. A decoded zero gap is not proof of audible continuity; exact-zero and low-amplitude measurements are diagnostics, not automatic trim points.
3. Exercise real iOS AVAudioFile/AVAudioConverter/AVAudioEngine and Android MediaExtractor/MediaCodec/AudioTrack output with original files. Record activeBackend, continuousFallbackReason, underruns, queue depth, scheduled/played/decoded frames, source identity and sample format around joins. Compare cold network playback, warmed MP3 cache and airplane-mode cached playback; use device/simulator output capture with the existing probe and distinguish simulator results from physical-device results.
4. Classify each defect: intrinsic source gap or discontinuity; MP3 priming/padding not removed correctly; resampling/converter issue; buffer starvation; native scheduling gap; decoder fallback. Fix the demonstrated cause in the narrowest shared layer, not a speculative Al-Juhany-only workaround. If source metadata is absent, do not treat quiet samples as disposable by default. Do not apply blanket silence trimming, fades, crossfades, time stretching or delete Quran pronunciation. Only correct objectively verified encoding padding/duplicated samples with independently validated sample-level evidence. If the source is already cut irreversibly, document the limitation; do not change providers or recordings without approval.
5. Expand the representative audit to every configured reciter (22): multiple contiguous verse boundaries, long ayah, differences in formats, Bismillah where appropriate. Use existing controller regression tests plus real-file native tests. Keep downloads reproducible and avoid committing full audio libraries. Report per-reciter source edge intervals, measured added output gap, sample integrity, underruns, fallback and pass/fail status separately.

### Production acceptance

Ordinary cached ayah transitions must not reinitialize audio output or add detectable avoidable gaps versus the correctly decoded reference (target 0 added PCM frames in a continuous output; report acoustic capture resolution separately). No omitted/repeated verse audio, broken pronunciation or additional fallback. Preserve original natural pauses. Maintain bounded rolling PCM buffers and low startup time; do not decode entire surahs into RAM or introduce persistent WAV caches. If hardware testing is unavailable, clearly report acceptance pending; do not claim all reciters sound seamless based on mocks.

## 3. Fix premature restart of a single long ayah

This is distinct from ordinary ayah joins. Direct selected-ayah playback in lib/main.dart sets fromAyah == toAyah and repeatCount: 1; restarting mid-ayah is not an expected repeat.

### Known recovery behaviour

lib/logic/quran_audio_controller.dart:
- _watchStall (around lines 497–505) starts a 30-second watchdog during loading/buffering/not-playing states; _recoverCurrent hands continuous playback to the legacy engine.
- _fallbackContinuous (1222–1266) captures the current occurrence, disposes the native output and calls _install(entry, generation, revision) without a position. _install defaults to Duration.zero. This deliberate safety behaviour is documented in docs/continuous-everyayah-engine.md and asserted by the existing fallback test (test/continuous_pcm_backend_test.dart, around 300–333).
- A decoder or route failure, append error or false stall can therefore restart an unfinished ayah. This is a confirmed code path consistent with the symptom, not proof of its actual trigger on the user's device.

### Reproduce and fix

- Use actual Al-Juhany long MP3s (2:255, 2:282 and additional long ayahs; include comparable Alafasy/other reciters). Test direct tap-to-play with repeat=1, range selection with repeat=1, intentional repeat=3, cached/uncached playback, foreground/background and Pause/Resume. Capture exact elapsed time and backend transition. Independently decode each original to confirm that it contains the full ayah and no intrinsic restart. Compare its hash to the cached file, validate complete MP3 frames and expected duration; verify cache replacement/redownload for a defective file.
- Instrument developer-only logs with reciter, surah/ayah, occurrence, repeat counter, generation/revision, last rendered position, buffered frames, native errors and fallback reason. Differentiate premature EOF, decoder error, output route reset, true buffer stall, false stall, and genuine repeat. Use the existing diagnostics rather than a new user-facing debug UI.
- Inspect packages/quran_pcm_audio/ios/Classes/PcmDecoder.swift and PcmOutput.swift/PcmFrameClock.swift for EOF, conversion and scheduling correctness over long recordings; inspect Android Mp3Decoder.kt and QuranPcmAudioPlugin.kt for MediaCodec stalls (15-second no-progress check), backpressure, decoded frame accounting and output completion. These are investigative targets, not proven defects.
- Fix the root cause first. In particular, distinguish genuine no-progress from healthy playback/backpressure and transient startup/loading events; a watchdog must not restart a long ayah simply because it has been playing for a long time. Never extend timeouts blindly, infer completion from MP3 duration estimates, or disable error recovery.
- Make recovery position-aware. Snapshot the last reliably rendered position and occurrence before teardown; preserve repeat counters, active selection, Play/Pause intent, queue ordering and cancellation generations. Prefer a bounded retry with the same decoder and verified sample offset when safe. For legacy fallback, use _install's position argument only when native-to-legacy position equivalence is verified for that recording/format and seek is reliable. Prefer a conservative verified recovery point that cannot skip Quran audio. If position cannot be trusted, retain the explicit safe recovery/retry path rather than silently skip recitation; log the reason. Do not create a new loop of silent automatic restarts.
- Ensure a successfully completed repeat=1 selection stops exactly once at true EOF. Only intentional repeat cycles may return to the beginning on successful completion. Preserve fallback's dispose-before-start guarantee and the existing pause/stop semantics.

Tests: extend test/continuous_pcm_backend_test.dart with simulated long timelines, advancing-clock vs no-progress stalls, injected mid-ayah errors, safe/unsafe resume, late native events, repeat=1 true EOF and intentional repeats. Update the existing zero-position fallback assertion to cover both verified resume and conservative fallback. Add real-file native regressions with Al-Juhany's actual long recordings on both platforms; compare decoded/output duration and sample sequence with an independent reference. Verify no spontaneous restart in repeated runs, no skipped or duplicated ayah content, correct highlighting/page-follow and background media controls. Run relevant legacy tests (audio_playback_test, audio_play_intent_test, audio_repository_test, continuous_pcm_backend_test, gapless_preparation_test, etc.).

## 4. Move the reader navigation dock to the right on folded devices

Scope is the existing floating reader dock (navigation buttons, zoom and audio controls), not the Android OS navigation bar or the navigator slide-in panel. Keep it identical in function and visual style; reuse the existing side-dock layout.

- lib/main.dart already passes foldedCover from IosDisplayRegions.closed for non-iPad devices into ReaderLayout.resolve. In lib/utils/reader_layout.dart the current bottom-dock condition chooses bottom for folded portrait. Override that condition only for a reliably detected folded cover, preserving the iPad precedence guard. Reuse DockPlacement.side and ReaderDock / ReaderDockPositioning from lib/components/reader_dock.dart, respecting control-region safe areas and the existing side controls. Ensure the side dock fits narrow cover screens, including expanded audio/ayah controls and zoom. Keep a sensible centered vertical position for folded cover, without altering standard landscape positioning.
- Preserve foldable page sizing: existing fitPages policy makes controls overlay rather than reserve page space. Do not change usableContentBounds, pageRegions, logical page focus, portrait/landscape mode, 100% zoom fitting, centring, page-turn animation, or the current page count. If changing dock placement indirectly changes a geometry branch, separate dock placement from page geometry so the pre-change page rectangles remain the same.
- Apply to all confirmed folded cover displays where a reliable runtime signal exists. Investigate Android's existing display-feature/native posture signals and MainActivity.kt; add supported detection only when it reliably distinguishes a folded cover from an ordinary phone, including rotation and initial launch while folded. A narrow aspect ratio, absent hinge, or tablet-sized inner screen history alone is not sufficient. If Android cannot reliably identify a particular device's cover, preserve existing behaviour and document device coverage rather than changing ordinary phones.
- Expected matrix: folded Duo portrait/landscape = right; supported Android cover portrait/landscape = right; unfolded portrait and landscape, half-open book and tabletop, ordinary iOS/Android phones, iPads and Android tablets = unchanged. Check posture transitions while the dock is open/closed and while audio plays.
